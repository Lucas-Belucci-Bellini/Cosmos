# Migration Audit — API recovery and Hermes integration (013)

**Date:** 2026-10-08  
**Scope:** Static inspection of the current `main` tree of Projeto-Baluarte and planning implications for Cosmos.  
**Status:** DISCOVERY / planning only. No endpoint was called, no credentials were inspected, and no tests or deployment checks were run.

## Executive finding

The assumption that the old API source code is entirely lost is **not confirmed**. The current Baluarte `main` tree still contains API-related files, including:

- `api/chat.py` — Gemini chat proxy;
- `api/hermes.py` — serverless proxy to a Nous Hermes model through an OpenRouter-compatible chat-completions endpoint;
- `api/health.py` — health/model/key-presence observation;
- `api/memory.py` — GitHub-backed memory endpoint;
- `api/nucleo.py` — authenticated event ingestion into Supabase;
- `api/claude.py` — Anthropic proxy;
- `backend/server.py` — optional FastAPI backend, including chat and observational contracts;
- `backend/transport_security.py` and related contract/test files.

This proves only that files are present in the inspected branch. It does **not** prove that they deploy, that environment variables or provider accounts are available, that old URLs are active, or that all frontend consumers still work. The Cosmos plan should therefore treat the old API implementation as **reference material to recover and evaluate**, while building new Cosmos contracts rather than blindly copying endpoints.

## Hermes clarification

In the inspected Baluarte implementation, `api/hermes.py` treats Hermes as a **model served by an external provider**, with a default model identifier `nousresearch/hermes-3-llama-3.1-70b` and an OpenRouter-compatible endpoint. This is different from adopting a complete agent/runtime project named Hermes. The first Cosmos prototype should explicitly choose which meaning is intended. For the current plan, the assumption is: **Hermes model/provider adapter for J.A.R.V.I.S., behind a provider-neutral interface**.

## Reusable design ideas (not automatic code migration)

- Keep provider credentials on the server; never expose them in browser bundles or Git.
- Separate health/observability from authorization. A health response must never imply that a caller is authorized.
- Keep a provider adapter behind a stable interface so the J.A.R.V.I.S. conversation/runtime does not depend on one model vendor.
- Use typed, bounded request/response contracts and explicit error mapping.
- Treat memory persistence as its own service/data contract rather than giving the model direct repository or database credentials.
- Keep tool execution outside the model adapter. Model output can propose a tool call, but the Cosmos runtime must validate its schema, authorize it, apply timeouts/quotas, and record a redacted audit event.
- Apply explicit CORS origin allowlists, request-size limits, rate limits, timeouts, and safe error responses.

## Risks observed for review before reuse

- `api/hermes.py` sets permissive `Access-Control-Allow-Origin: *`, returns provider/server exception details in a response field, and does not visibly enforce authentication or rate limiting.
- Several serverless handlers respond with HTTP 200 for configuration/provider failures, making operational failures hard to distinguish from success.
- `api/memory.py` is designed around a GitHub token and writes memory into a repository branch; this must not be adopted as Cosmos' durable memory architecture without a privacy, concurrency, and data-retention decision.
- `api/nucleo.py` uses a privileged Supabase key server-side. Any replacement must preserve secret isolation and validate authorization, payload size, rate limits, and allowed event types.
- Legacy model names, provider endpoints, URLs, and environment variable names may be stale; verify them at implementation time rather than treating comments as current truth.

These are static review observations, not proof that a deployed service is exploitable. Validate each risk with tests in a controlled environment before drawing a runtime conclusion.

## Target architecture proposal

1. **J.A.R.V.I.S. UI (TypeScript):** sends a versioned conversation request to Cosmos API; it never receives provider secrets.
2. **Cosmos API boundary:** validates payload size/schema, identity, quotas, request IDs, and authorization; emits normalized errors.
3. **Conversation orchestrator:** builds bounded context from approved memory/knowledge and chooses a provider adapter.
4. **Hermes provider adapter:** maps Cosmos messages to the selected provider's API and normalizes responses, timeouts, token usage, and provider errors.
5. **Tool runtime:** validates model-proposed tool calls against the server-owned catalog and schema; independently authorizes each operation; never executes arbitrary model text as code.
6. **Memory/data layer:** stores approved memory in Cosmos' chosen SQL/data architecture with user/tenant isolation and explicit retention.
7. **Observability:** records request IDs, latency, model/provider identifiers, result category, and redacted failure codes; never logs API keys, tokens, or full private conversations by default.

## Required decisions before implementation

- Confirm whether “Hermes” means the Nous Hermes model via a provider API, the Hermes agent/runtime project, or both.
- Choose the provider and verify model availability, pricing/quotas, terms, and environment-variable configuration.
- Define the versioned request/response/error contract and maximum message/history sizes.
- Decide whether memory is session-only or persistent, and define retention and deletion behavior.
- Define identity and server-side authorization before enabling remote or local tools.
- Decide deployment target and health/readiness semantics.
- Specify mock-based tests so core behavior is testable without live provider credentials.

## Decision

**REBUILD API contracts; REFERENCE legacy implementation; VERIFY recoverability.** Do not declare the APIs lost solely because the service stopped working, and do not declare them recovered merely because source files exist. Treat Hermes as a replaceable model/provider adapter until the user explicitly selects a broader Hermes runtime.
