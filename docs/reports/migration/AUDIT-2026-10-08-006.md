# Auditoria de migração — AUDIT-2026-10-08-006

## Escopo

Inspeção estática adicional do Data Layer do Projeto-Baluarte para identificar comportamentos de storage, autenticação e acesso remoto que devem ser preservados ou redesenhados no Cosmos.

Origem: Projeto-Baluarte, branch padrão consultada no momento da auditoria. Destino: Cosmos.

## Arquivos reais inspecionados

### 1. `src/core/storage.ts`

Comportamentos confirmados no código:
- Prefixa chaves com namespace `baluarte:`.
- Usa `localStorage` quando disponível e um `Map` em memória como fallback.
- Registra schemas por chave com versão, classe e função de migração.
- Usa envelope versionado `{ __bv, d }` para dados com schema.
- Se encontra versão armazenada mais nova que a versão do código, devolve fallback e preserva o dado.
- Se a versão antiga não tem migrador, devolve fallback e não tenta inventar uma conversão.
- Classifica dados em `publico`, `local`, `sensivel` e `secreto`; gravação de classe `secreto` no storage do frontend é rejeitada.
- Expõe estado de schemas registrados e versões persistidas.

Implicação: Cosmos precisa de contrato explícito de persistência e migração, mas o formato de envelope e o namespace não devem ser copiados sem avaliar consumidores e compatibilidade. Dados secretos não podem ser armazenados no navegador como se fossem protegidos.

### 2. `src/core/auth-session.ts`

Comportamentos confirmados:
- Projeta respostas de autenticação para um formato de sessão conhecido.
- Valida tokens como strings não vazias e expiração como valor positivo.
- Suporta `expires_at` e `expires_in`, incluindo TTL padrão documentado.
- Projeta refresh de sessão com fallback para o refresh token anterior quando o provedor não retorna outro.

Implicação: preservar a validação de formato e expiração como comportamento testável; não migrar tokens/sessões reais do Baluarte para o Cosmos. A decisão sobre armazenamento de sessão deve seguir o provedor de identidade e o modelo de ameaça do Cosmos.

### 3. `src/core/supabase.js`

Comportamentos confirmados:
- Cliente leve que chama PostgREST/Auth por `fetch`, sem SDK Supabase.
- Lê configuração de variáveis Vite/ambiente e contém fallback para um projeto Supabase legado.
- Usa timeout padrão de 8 segundos para requisições.
- Normaliza respostas JSON/texto e converte falhas de rede/timeout em erros com contexto.
- Expõe operações genéricas de leitura, inserção e RPC.
- O comentário do próprio arquivo alerta que RPC com `SECURITY DEFINER` pode executar com privilégios elevados e requer atenção à segurança.

Implicação: não transportar o fallback de projeto legado para Cosmos. Definir configuração obrigatória por ambiente e contratos de endpoint. Auditar cada RPC/função privilegiada, autorização, RLS, limites de entrada e logs antes de qualquer adoção.

### 4. `src/core/permissions.ts`

Comportamentos confirmados na parte inspecionada:
- IDs de permissão seguem formato validado `dominio.acao`.
- Risco padrão é restrito.
- Permissões desconhecidas/inválidas geram erro explícito.
- Curingas não alcançam permissões de risco restrito.
- Concessões e revogações são registradas em auditoria limitada e emitem eventos.

Implicação: Cosmos precisa de autorização de servidor para operações protegidas; um gerenciador de permissões no frontend não pode ser a única barreira de acesso ao PostgreSQL.

### 5. `docs/v2/PHASE_00_AUDIT.md`

O relatório histórico descreve uma plataforma monorepo com frontend, Core V1/V2, runtime Rust, scripts Python, migrações Supabase, desktop, Android e workflows. Também registra lacunas conhecidas de cobertura e automação do Data Layer. O estado histórico não é tratado como status atual do Cosmos e não substitui testes executados no destino.

## Decisões preliminares Baluarte → Cosmos

| Capacidade | Decisão | Requisito Cosmos |
|---|---|---|
| Storage com schema/versão | REBUILD/ADAPT | Contrato de persistência, migração explícita, fallback e teste de versão futura |
| Fallback local | ADAPT | Declarar quando é apenas cache/offline e como sincroniza com PostgreSQL |
| Classes de dados | REBUILD | Política de classificação independente e enforcement também no servidor |
| Projeção de sessão | REFERENCE/REBUILD | Validar expiração e resposta do provedor; nunca importar tokens legados |
| Cliente PostgREST genérico | REBUILD | API/repositórios Cosmos com configuração por ambiente e allowlist de operações |
| RPC privilegiada | REFERENCE, revisar uma a uma | Auditoria de função, privilégios mínimos, RLS, validação e testes negativos |
| Permissões frontend | REFERENCE/REBUILD | Autorização server-side e negação por padrão |

## Relação com SQL

O PostgreSQL permanece alvo central SQL conforme ADR-0002. O storage de navegador pode servir preferências não sensíveis ou cache, mas não substitui a fonte de verdade relacional. O Cosmos não deve criar tabelas apenas para espelhar cada chave do localStorage; cada entidade precisa de caso de uso, dono, retenção, relações e autorização definidos.

## Limites

- Esta foi uma inspeção estática de arquivos; não executou testes do Baluarte ou Cosmos.
- Nenhuma chamada foi feita ao banco Supabase legado e nenhuma tabela/dado remoto foi alterado.
- Não foi feita migração de código, token, sessão, schema ou segredo.
- A presença de métodos no código não prova que todos os consumidores estejam corretamente autorizados.
